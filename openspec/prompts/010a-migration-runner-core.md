## Scope and process
Implement a forward-only, checksum-verified migration engine for SQLite `quant_state.db` and DuckDB `quant_flow.duckdb`. 010a uses **synthetic fixtures only**; 010b owns real baselines. In PROPOSE produce only proposal.md, design.md, tasks.md and OpenSpec spec deltas. No source, archived 005/005a-d, or `docs/reference/CURRENT` edits. Follow AGENTS and the existing Clock port. No runtime DDL outside the runner. Test DBs always use temporary paths, never `/data`.

Before any APPLY-phase commit, verify `docs/reference/CURRENT/ARCH_v5.1.5.1_Vol3_Capture_AntiDetection.md` SHA-256 equals `2d7a90e533196af61745bc4efd3259b7b64b519b8ec78662392b50a911285e23`; abort on mismatch. Never modify anti-detection logic or ARCH V3 §F.

## Binding design decisions (record D1–D15 in design.md)

**D1–D4 — layout/API.** Flat `migrations/{sqlite,duckdb}/NNN_<slug>.sql`; code `src/quantflow/migrations/{runner,manifest}.py`; single `migrations/MANIFEST.json`; Typer CLI in existing `src/quantflow/cli`. No down migrations. Manifest entry has `{id, store, path, sha256, applies_after, component, enabled}`; additionally record `baseline_covered` in a documented, validated per-store manifest metadata section when 010b adds real baselines. `applies_after` is ALWAYS an array of IDs (`[]` for root), not a scalar; dependencies are store-local unless an explicitly designed cross-store dependency feature is separately approved (not in scope).

**D5 — slots.** For v2.0.5.1, NEVER: SQLite 072–079, DuckDB 046–049; any manifest entry there is an error. DuckDB 046 is *reserved for a future phase*, not prohibited forever: changing the policy requires a later reviewed code/spec change. ADOPT-ONLY: DuckDB 043–045 and 050, SQLite 071; no auto-apply until explicit operator-approved enablement. All other entries must be explicitly classified and validated. Unmanifested SQL files are an error. 051/052 are handled by 010b, not assumed valid by 010a.

**D6 — state machine (replaces incorrect fresh definition).** `schema_version_<store>` is a ledger table name **only if confirmed by SPEC V2 §19**; use exact SPEC DDL and naming, not an invented schema. A fresh store has no application schema and no successful baseline ledger row. A ledger with an OK baseline is *already baselined*, not fresh. An existing legacy store without a baseline ledger is **NOT** fresh and must not be overwritten or silently adopted: abort pending an explicit 010b adoption plan. A ledger that exists but is empty is eligible for baseline only if independent schema inspection confirms the database contains no pre-existing application tables. The bootstrap ledger itself is excluded from that emptiness check.

**D7 — ledger bootstrap and atomicity.** Bootstrap the SPEC-defined ledger in its own committed transaction **before** any migration. Do not include ledger creation in the transactional baseline payload. On migration failure: rollback migration DDL and its OK insert; in a new transaction insert/update a single FAILED ledger record, then abort. A failed migration must never leave partial DDL. If the SPEC ledger cannot represent repeated attempts or the prescribed failure record without constraint violations, STOP and propose a SPEC-compatible resolution rather than changing its DDL silently. Bootstrap failure is surfaced as a hard error, not falsely recorded as a migration failure.

**D8 — app version (resolved).** Use `importlib.metadata.version("quantflow")` as the sole application-version source for ledger writes. If package metadata is unavailable, fail with an actionable packaging error; never silently use `unknown`, hard-coded `v2.0.5.1`, or an arbitrary fallback. 010b baseline rows use the same source at the time of installation/adoption; subsequent migration rows use the version at their own application time.

**D9 — dual-store.** `--store both` runs SQLite then DuckDB, reports each result independently, and offers no cross-store atomicity. DuckDB failure does not roll back a committed SQLite migration. Do not silently claim both stores succeeded.

**D10 — baseline ledger identity.** Reserve migration ID **`000_baseline`** (store-local), represented as an ordinary manifest entry with `path` and SHA-256. Its ledger `migration_id` is exactly `000_baseline`; `checksum` is the lowercase SHA-256 of the exact immutable SQL file bytes; `app_version` comes from D8; `result='OK'` only on successful baseline commit; `applied_at` comes from the Clock port (EpochMs). Confirm that these values and ID fit the actual SPEC schema; if not, block 010b and document the necessary contract amendment. Never invent a checksum sentinel.

**D11 — baseline dependency closure.** `000_baseline` is an actual successful ledger row, not a virtual or ignored migration. A post-baseline migration with `applies_after: ["000_baseline"]` passes closure only when the corresponding store's OK baseline row exists. For an existing store, 010b must explicitly reconcile covered historical IDs and post-baseline migrations; do not infer that a dependency is satisfied just because its table exists. `baseline_covered` is informational history only, never a fabricated OK ledger row. Dependency IDs must exist in the same store's manifest or in explicitly validated baseline coverage with documented closure semantics; prefer direct dependency on the baseline for freshly introduced post-baseline migrations.

**D12 — FAILED handling.** A FAILED record blocks further `apply` by default (no implicit retry). `status` reports it and `verify` fails. Recovery requires operator investigation and an explicit, audited retry workflow proposed in design.md (e.g., dedicated `--retry-failed` if compatible with the CLI and SPEC). Retrying is allowed only after proving no partial schema changes and that the file checksum matches the failed attempt; a successful retry must leave a single unambiguous OK state per migration. If the ledger's keys cannot support this, STOP for a contract decision. No automatic retry-once.

**D13 — SQL execution.** Python SQLite `sqlite3.Connection.executescript()` is **forbidden** for transactional migrations because it may commit implicitly. Use `isolation_level=None`, explicit `BEGIN`/`COMMIT`, and a reviewed SQL statement execution strategy that correctly handles semicolons in triggers/quoted text. Do not naively split on `;`. DuckDB also uses explicit per-migration transactions. Reject statements that cannot run transactionally; prove rollback with fault injection. Apply required connection settings outside transactions.

**D14 — connection policy.** Embedded quantd mode uses the quantd-owned SQLite connection with its already-established PRAGMAs, checking required settings without mutating them inside a transaction. Standalone CLI opens a separate connection only when quantd is stopped and sets `PRAGMA journal_mode=WAL`, `PRAGMA synchronous=NORMAL`, `PRAGMA foreign_keys=ON`, and `PRAGMA busy_timeout=5000` before `BEGIN`; verify the values, and refuse incompatible state. Do not open a competing writer. For DuckDB set `temp_directory` before opening the write connection, using the application's documented path policy; do not invent a `/data` path for tests. Confirm any repo-specific differences in design.md before implementation.

**D15 — verify contract.** `migrate verify` is strictly read-only and checks: manifest schema and required fields; uniqueness and store-local dependency existence; acyclic ordering; unmanifested SQL files; slot policy; on-disk SHA-256 against manifest; every OK ledger row has a manifest entry and identical checksum; baseline identity and presence where required; every applied migration has satisfied dependency closure; no FAILED rows; no unexpected DB-newer-than-code rows. Report pending enabled migrations as `PENDING` without treating them as corruption (exit 0 if otherwise consistent); status must show pending count and each store's last successful migration. Exit 0 = consistent, 1 = validation/drift/failure, 2 = CLI/usage/configuration error. Never write a ledger, set mutating PRAGMAs, or create a database in `verify`/`status`; missing stores must be reported explicitly. A separate 010b schema-parity test verifies actual runtime schema against SPEC and is not replaced by `verify`.

## Implementation and tests
1. Manifest validator: path safety, required keys/types, SHA-256, ID uniqueness, reserved slots, unmanifested files, cycle/closure detection, stable topological order (numeric ID tie-break, baseline first). Never use `MAX(migration_id)` as ordering.
2. Ledger bootstrap and fresh/legacy detection, immutable baseline row and checksum, explicit Clock timestamps.
3. Atomic runner for both stores, explicit failed-state and recovery design, package version handling, no `executescript`.
4. CLI `quantflow migrate apply|status|verify [--store sqlite|duckdb|both]`; if adding explicit retry, document approval and audit semantics.
5. Tests using tiny synthetic migrations and `tmp_path`: checksum mismatch; duplicate IDs; idempotent OK; NEVER/ADOPT-ONLY; unmanifested file; cycles; stable topo; failure rollback + exactly one FAILED record; FAILED default abort; DB-newer; baseline dependency closure; first-boot/empty-ledger/legacy distinctions; no `executescript`; PRAGMA modes; read-only verify and exit codes; dual-store partial failure; schema equivalence of fresh vs upgrade for closed manifest subsets. Canonical SQLite `sqlite_master` and DuckDB table/column introspection; do not demand byte-identical DB files. Integration suite target <10s.

## Spec deltas / acceptance
Migration runner capability: forward-only, immutable checksums, SPEC-defined authoritative ledger, `result IN ('OK','FAILED')`, no IN_PROGRESS, dependency closure, explicit failure policy and non-mutating verification. Consume existing epoch-clock port; do not modify it. Verify with `uv run pytest -q`, `uv run ruff check src tests`, `uv run ruff format --check src tests`, `uv run mypy --strict src/quantflow`, coverage >=95% for `domain/**` and `migrations/**`, `python3 scripts/check_constants.py`, anti-detection SHA gate, clean `git status --short` without `.bak`. Tag `feature-010a-complete` only after merge and successful checks.

## Stop conditions
Do not run apply if actual SPEC §19 ledger DDL conflicts with D7/D10/D12, if a pre-existing legacy DB cannot be distinguished from fresh, or if transactional execution cannot be proven. Surface the exact conflicting SPEC line and request a reviewed design decision. 010a itself must not create real 010b baseline SQL.
